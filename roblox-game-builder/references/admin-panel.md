# Индивидуальная админ-панель игры

Явное общее указание пользователя от 15 ноября 2026: при создании игры делать админ-панель для разработчика; определять её содержимое по системам игры и поддерживать актуальность при последующих добавлениях. Реализуй рабочие команды, не только декоративный интерфейс. Текущий запрос изменяет скилл, а не поручает менять все существующие игры сразу.

## Состав по фактической игре

Перед реализацией составь перечень валют, сохраняемых характеристик, прогрессии, каталогов предметов и особых систем. Используй реальные схемы и сервисы проекта; не придумывай отсутствующие характеристики. Например:

- Валюты/ресурсы: добавить, установить, вычесть количество; выбор существующей валюты.
- Уровень/опыт/перерождения: установить и изменить через сервис прогрессии с согласованными производными значениями и открываемыми возможностями.
- Предметы, питомцы, инструменты: поиск по каталогу, выбор ID/варианта и количества, выдача и удаление, если это поддержано механикой; учитывать вместимость и уникальность экземпляров.
- Зоны, задания, улучшения и другие фактические системы: подходящие операции открытия, установки стадии или сброса.
- Прогресс: сброс собственного профиля целиком или выбранной подсистемы с ясно указанным объёмом и подтверждением внутри панели.

Не добавляй ненужные разделы ради универсального шаблона. Основная цель по умолчанию — собственный игрок администратора. Управление другими игроками и массовые действия не следуют автоматически из этого пожелания. Не имитируй покупки/чеки и не выдавай внешнее владение платным ассетом: тестовая выдача игрового предмета — отдельная операция.

## Один реестр вместо ручных списков

Связывай панель с действующими каталогами предметов, валют и схемой характеристик. Серверный реестр администрирования хранит стабильный ID, подпись/раздел, допустимые операции, тип/диапазон параметров, обработчик сервиса, правила доступа и подтверждения. Клиент получает только разрешённые описания для построения формы; обработчики и право выполнения остаются на сервере.

Панель строит поиск, списки и поля из этих описаний, а не из независимо захардкоженных названий. При добавлении предмета в существующий каталог он появляется в соответствующем списке без ручного дублирования кнопок. При добавлении валюты/характеристики/новой системы одновременно регистрируй её допустимые команды и обработчики. Не открывай произвольную запись всех полей профиля: внутренние ключи, служебные метки и вычисляемые значения не являются редактируемыми характеристиками. Вычисляемый параметр изменяется через свой источник, например уровень через согласованный сервис опыта/прогрессии.

При каждом изменении механики проверь охват админ-панелью. При переименовании/удалении ID обновляй команды и миграции, убирай устаревшие варианты. Если каталоги изменяются во время сессии, обновляй разрешённые списки по версии/событию или при повторном открытии; сервер всегда проверяет актуальный ID. При сохранении шаблона UI в библиотеку выноси игровые каталоги и разрешения в параметры, не копируй реальные профили или права конкретной игры.

## Серверное выполнение и сохранение

Доступ проверяется на каждом запросе по настроенному списку Roblox UserId разработчика/администраторов. Не полагайся на скрытую кнопку, имя игрока, клиентский флаг или переданный клиентом actor/target. Для игры группы её ID не равен UserId разработчика. Если UserId не установлен достоверно, оставляй доступ закрытым и явно сообщай, какое поле настройки ещё требуется; не открывай панель всем.

Проверяй команду, типы, конечные числовые значения, диапазоны, ID, количество, права и частоту запросов. Не допускай произвольного исполнения Luau, путей к объектам или записи полей по строке клиента. Обработчики вызывают обычные серверные сервисы экономики/инвентаря/профиля, чтобы HUD, сохранения и остальные системы видели единое состояние. Менять только leaderstats или текст UI недостаточно.

Для сохраняемого прогресса изменения идут через текущий загруженный профиль и штатный механизм сохранения. Сброс отменяет связанные отложенные награды/операции, восстанавливает согласованный профиль и обновляет клиент; старый autosave не должен вернуть прежние данные. Ошибка сохранения отображается честно, без ложного «сохранено». Повтор запроса не должен дважды выдавать награду; учитывай request ID и результат операции. Веди компактную серверную запись actor, команды, цели, параметров, времени и результата для разбора ошибок.

## Интерфейс и проверка

Применяй [стандарт UI](ui-quality.md): сворачиваемая панель, разделы/поиск, понятные текущие значения и результат команды, отсутствие перекрытия управления в закрытом состоянии. Для сброса явно покажи выбранную область и потребуй подтверждение в самой игре. Это поведение панели, а не необходимость спрашивать разрешение на каждую правку скилла.

Проверяй на тестовых данных: авторизованный разработчик выполняет команды; обычный игрок не может выполнить их даже прямым запросом; неверный ID/число и повтор запроса не ломают состояние; новый предмет и новая характеристика доступны в панели; изменение отражается в игре и после повторного входа; сброс не откатывается старым сохранением. Не сбрасывай реальные профили ради проверки. Не заявляй игровую проверку при одном чтении кода. Для небольшой несвязанной правки старой игры не перестраивай всю архитектуру панели без задачи; если правка добавляет предмет или характеристику, включай её в существующую панель в рамках этой же работы.
